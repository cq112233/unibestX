## 11.1 从业务主体出发，不要从组件库出发

设计不是「把页面填满」，也不是「套一套好看的卡片」。开始写 `.uvue` 之前，先用一句话回答：

| 问题 | 必须给出的答案 |
| :--- | :--- |
| 这是什么产品 | 例如：食堂餐补核对系统、设备巡检工具、校园活动报名 |
| 谁在使用 | 例如：财务人员、门店店长、首次注册的学生 |
| 这个页面只完成什么任务 | 例如：找到一笔异常餐补并处理，而不是「展示所有数据」 |
| 用户此刻最关心什么 | 例如：异常金额、处理进度、下一步按钮 |
| 业务的独特语境是什么 | 例如：票据感、批次感、时间线、审批流、现场巡检 |

视觉语言应从业务本身生长出来：材料、行业术语、数据结构、工作节奏、真实场景都能成为设计线索。面向财务核对页和面向儿童活动页，即使组件库相同，也不应该得到同一种气质。

如果需求描述不完整，先在实现前列出**明确假设**，不要用通用模板填空。已有页面改版时，还要先确认它是「视觉重做」还是「结构调整」；**默认保留已有信息架构、页面 URL 与业务入口**。

### 反例与正例

```text
❌ 反例：先打开组件库，挑一组卡片、渐变和阴影，再想内容放哪里。
✅ 正例：先确定「谁在什么场景下完成什么任务」，再决定需要哪些信息层级和交互。
```

## 11.2 先写紧凑设计计划，再做两轮批判

这是一个**两遍流程**，不能跳过：

1. **第一遍：写设计计划** —— 先用短文档确定主题、受众、任务、颜色、字体、布局、signature 与明确不采用的方向。
2. **第二遍：自我批判** —— 逐项问「如果换成一个完全不同的业务，这个方案是否仍然成立？」如果成立，它大概率是通用默认，不是为当前业务做的选择；修正后再写代码。

### 设计计划模板

```md
- 业务主体：
- 受众：
- 页面唯一任务：
- 用户最重要的下一步：
- 业务语境 / 视觉线索：
- Color（4–6 个具名十六进制）：
  - canvas: #......
  - surface: #......
  - ink: #......
  - muted: #......
  - accent: #......
- Type：
  - display：
  - body：
  - utility（仅在确有需要时）：
- Type scale（3–5 级）：
- Layout（一句话 + ASCII 线框）：
- Signature（唯一记忆点）：
- 明确不采用：
- 平台与状态约束（App / 小程序 / H5；空 / 错 / 加载 / 无权限）：
```

### 设计计划的正反例

```text
❌ 通用计划：
  「现代、简洁、科技感；蓝色；卡片布局；圆角阴影；渐变按钮。」

✅ 业务计划：
  「财务批量核对页。受众是每天处理大量餐补流水的财务人员，唯一任务是从批次中找出异常并完成处理。
  主视觉用票据式横向行、等宽数字和窄幅状态标记；强调色只用于异常金额与处理按钮。
  signature 是顶部批次条带：批次号、时间范围、异常数依次排列。其余区域保持低对比。”
```

## 11.3 颜色：先命名 Token，再使用颜色

### 11.3.1 基础色控制在 4–6 个

基础色不是「这个页面能用的所有颜色」，而是构成视觉骨架的核心集合：

| Token | 作用 | 选择原则 |
| :--- | :--- | :--- |
| `canvas` | 页面底色 | 与产品场景一致，不要默认奶油色或近黑色 |
| `surface` | 卡片 / 面板 / 输入区 | 与 canvas 有可感知但克制的层级差 |
| `ink` | 主文字 | 保证正文对比度，不用纯黑凑「高级感」 |
| `muted` | 次要文字 / 辅助信息 | 仍要可读，不能用极浅灰隐藏关键信息 |
| `accent` | 唯一主强调色 | 只服务于主操作、当前状态或 signature |
| `border`（可选） | 分隔与边界 | 比阴影更适合信息密集页面 |

成功、警告、危险、禁用等**语义状态色**可以超出这 4–6 个基础色，但必须语义稳定：同一个红色不能一会儿表示删除、一会儿表示品牌装饰。

### 11.3.2 全部使用十六进制

- Tailwind 与 Stylelint 一律使用 `#ffffff`、`#0f172a`，禁止 `red`、`white`、`gray` 等命名颜色。
- 不与主题联动的固定色直接写十六进制；需要跟随换肤的颜色走 `useThemeStore()` / CSS 变量。
- 动态颜色走 `:style` 或 AppText 的 `color`，不要在静态 class 与动态 style 之间来回覆盖。
- 同一个语义只保留一个颜色来源，禁止页面 A 写死、页面 B 用变量、页面 C 再近似取值。

### 11.3.3 避免「AI 默认色板」

以下色板可以使用，但只有在 brief 明确要求或确实最符合业务时才使用；不能因为「看起来高级」就默认选择：

1. 奶油底 + 高对比衬线 + 陶土橙强调色；
2. 近黑底 + 单一荧光绿 / 朱红强调色；
3. 大面积紫蓝渐变 + 玻璃卡片 + 发光按钮；
4. 所有层级都使用同一个低饱和灰蓝，导致主次完全消失。

## 11.4 字体与排版：让层级承载信息

### 11.4.1 字体数量与角色

- 优先使用**一个字体家族**；最多两个，且两个角色必须明显不同。
- 系统字体是移动端的可靠默认；引入品牌字体必须有业务理由，并确认文件可访问、授权明确、加载失败时能回退到系统字体。
- 字体家族通过 `AppText` / 内联 `font-family` 统一管理，禁止 `font-mono` / `font-sans` 工具类。
- 正文与标题的差异优先来自**字号、字重、行高、留白**，而不是不断更换字体。
- 图标字体、`uni-icons`、第三方组件内部文字**不要替换成 AppText**，避免全局字体族破坏图标。

### 11.4.2 字号层级控制在 3–5 级

一个页面通常只需要：

| 角色 | 建议基值 | 用途 |
| :--- | :--- | :--- |
| `title` | 20px / bold / 28px | 页面唯一主标题 |
| `subtitle` | 16px / bold / 24px | 区块标题、关键对象名 |
| `body` | 14px / normal / 22px | 正文与主要信息 |
| `label` | 13px / 500 / 20px | 表单标签、短操作文案 |
| `caption` | 12px / normal / 18px | 辅助说明、时间、状态补充 |

这些是起点，不是每页必须全用。**不要出现 11、12、13、14、15、16、17、18px 同时存在却没有语义理由的层级碎片**。

### 11.4.3 AppText 是业务文案的默认载体

需要跟随全局字体与字号缩放的业务文案，统一使用 [AppText.uvue](../../../../src/components/AppText/AppText.uvue)：

```html
<view class="flex flex-col px-[16px] py-[12px]">
  <AppText variant="title" class="text-[#172033] mb-[4px]">餐补发放明细</AppText>
  <AppText variant="body" class="text-[#526071]">
    共 36 笔，异常 2 笔
  </AppText>
  <AppText variant="caption" class="text-[#7b8794] mt-[8px]">
    数据更新于今天 09:40
  </AppText>
</view>
```

职责边界：

- `variant` 管字号、字重、行高与语义层级；
- `class` 管颜色、间距与布局，**不要再叠字号 / 字重 / 行高工具类**；
- `size` / `weight` / `lineHeight` 只用于局部确有必要的覆盖，不作为默认写法；
- 动态颜色使用 `color` 属性，例如 `:color="themeStore.state.theme"`；
- 所有文字颜色与字体样式必须落在 `<text>` 或 AppText 的根 `<text>` 上，严禁挂到 `<view>`。

全局字体和字号缩放由 `useFontStore()` 统一管理：

```uts
import { useFontStore } from '@/src/store/index.uts';

const fontStore = useFontStore();
fontStore.setFont('alimama-daoli');
fontStore.setFontScale(1.1);
```

### 11.4.4 常见排版反模式

- **只给标题里的一个词换色 / 加粗 / 斜体**，把它当作「设计感」；除非该词真的承载语义，否则不要做。
- **每个标题上方都加全大写 eyebrow**，内容并没有分类功能，只是通用模板装饰。
- **滥用等宽字体**表示「技术感」；只有编号、时间、金额、代码等需要对齐的数据才考虑等宽。
- **字号单位混用**：uni-app X 只使用 `px`，禁止 `em` / `rem` / `%` / `vw` / `vh`。
- **中文长文行过长**：移动端正文通常控制在约 18–24 个汉字一行，过宽会显著降低扫读效率。

## 11.5 结构就是信息：让分隔、编号与标签有语义

视觉结构应该帮助用户理解内容，而不是装饰内容。

| 结构元素 | 只有满足以下条件才使用 |
| :--- | :--- |
| `01 / 02 / 03` | 内容确实是步骤、顺序、时间线或优先级序列 |
| 分割线 | 需要表达「信息组切换」或「不同层级边界」 |
| 侧边竖线 | 需要表达引用、审批链、时间轴或分组归属 |
| eyebrow / 小标签 | 需要补充分类、状态、批次、来源等真实信息 |
| 徽标 / 角标 | 需要提示数量、异常、未读、状态变化 |
| 阴影 | 需要表达浮层与底层关系；普通信息分组优先用留白与边框 |

如果没有序列关系却加编号，没有分类关系却加标签，用户会误以为它们携带信息，反而增加理解成本。

### 首屏先给业务，不给装饰

用户进入页面首先看到的区域，应直接呈现这个业务最有代表性的内容：一个待处理的异常、一个当前批次、一个正在进行的任务，或唯一的主操作。可选形式包括关键对象、真实数据、任务入口或服务状态。

「大数字 + 小标签 + 渐变强调」是一种常见但并非默认正确的 hero 方案；只有当它确实是当前页面最有效的表达时才使用，不能因为它最容易生成就套上去。

### 布局原则

- 移动端优先，先设计窄屏信息顺序，再考虑宽屏留白。
- 只用 flex；禁止 `grid`、`inline-block`、`position: sticky`。
- 不允许 `gap` / `space-x-*` / `space-y-*`；用 `mt-*` / `mb-*` / `ml-*` / `mr-*` 建立节奏。
- 同一页面使用统一的间距阶梯，例如 `4 / 8 / 12 / 16 / 24 / 32px`，不要随手写 `13px`、`19px`、`27px`。
- 页面高度不手写 `100vh`，使用布局与 `@/src/utils/systemInfo` 提供的可用高度。
- 底部与安全区使用 `p-safe` / `pt-safe` / `pb-safe`，不要手写 `env(safe-area-inset-*)`。
- 关键触控区域建议不小于 `44px × 44px`；文字小不等于点击区域可以小。

### 线框先于代码

先用 ASCII 比较两种信息顺序，再决定代码结构：

```text
方案 A：批次优先                        方案 B：异常优先
┌──────────────────────────┐          ┌──────────────────────────┐
│ 批次标题 + 时间范围       │          │ 异常金额 + 处理入口       │
│ 汇总数字                  │          │ 批次与时间范围            │
│ 明细列表                  │          │ 明细列表                  │
│ [导出] [处理异常]         │          │ [处理异常]                │
└──────────────────────────┘          └──────────────────────────┘
```

财务核对场景通常应让「异常」先于「全量明细」；后台监控场景则可能先给批次上下文。线框的价值是暴露这种取舍，而不是画得漂亮。

## 11.6 动效：一次主节奏，胜过满屏散点动画

- 优先设计**一个**有明确目的的动效：页面首次进入的关键信息出现、Tab 切换的当前状态变化、提交后的成功确认。
- 动效必须回答「发生了什么变化」，而不是给每个卡片都加同款 fade-and-slide-up。
- 点击反馈优先使用状态变化、按压态、颜色与位置变化；不要依赖 hover —— 小程序的触摸场景没有 hover。
- 动画样式固化在静态 class 中，动态部分只切换 class；不要把所有关键帧塞进动态 `:style`。
- 关键信息必须在动画未执行时仍然可见、可操作；动画不能成为完成任务的唯一提示。
- 连续、循环、强闪烁动画只有在业务本身需要时才使用（例如实时监控中的状态脉冲），并且必须保证信息不只依赖动画传达。

```html
<!-- ❌ 反例：所有卡片都做同一套入场动画，页面没有主次 -->
<view class="card-enter" v-for="item in list" :key="item.id">...</view>

<!-- ✅ 正例：只给本次操作产生的结果做一次确认反馈 -->
<view class="flex flex-row items-center" :class="saved ? 'save-confirmed' : ''">
  <text class="text-[#166534] text-[14px]">{{ saved ? '已保存' : '保存修改' }}</text>
</view>
```

## 11.7 克制：大胆只花在一个地方

- 页面只保留**一个** signature：一个独特的批次条带、一条有业务含义的时间轴、一种只属于该产品的数据呈现方式，或一个识别度高的主操作。
- signature 之外的模块保持安静：统一间距、统一字号层级、统一边框或留白规则。
- 删除不服务任务的装饰：无意义的渐变、重复图标、装饰性统计、每个区块都出现的卡片壳。
- 可用「香奈儿原则」自检：完成页面后，再拿走一个配饰，看信息是否更清楚而不是更空洞。
- 大胆不等于复杂。一个高对比标题、一个精确的色块、一个独特但可解释的布局，通常比十种效果更有效。

## 11.8 避免模板化审美：这些「默认答案」要有理由

以下做法在某些业务里完全合理，但它们经常在没有思考 brief 时自动出现。若没有明确的业务理由，不要直接使用：

1. **SaaS 卡片套件**：所有区块都是相同圆角、相同阴影、相同内边距的卡片，层级完全靠「再套一层卡片」。
2. **渐变装饰**：用紫蓝渐变、玻璃拟态和发光按钮代替信息结构。
3. **假数据美学**：大量漂亮的「99.9%」「128,492」和动态图表，却没有真实业务含义。
4. **统一圆角**：标题、正文、按钮、头像全部同一个圆角，视觉重量没有被区分。
5. **模板 chrome**：每个标题都要有 eyebrow、每个链接都要加 `→`、每个标签都用「A · B · C」的中间点拼接。
6. **无意义编号**：不是流程也放 `01 / 02 / 03`，让用户误以为存在顺序。
7. **满屏图标**：每个功能项都配一个风格不统一的图标，结果图标比信息更抢眼。

开发者明确指定了视觉方向时，**brief 优先**。例如业务明确要求玻璃质感，就做玻璃质感，但要让可读性、层级与交互状态成立，而不是只复制一个流行外观。

## 11.9 文案也是设计材料

界面文案的任务是让用户更容易理解和操作，不是填充空白。

- **从用户视角命名**：用「餐补明细」而不是「SubsidyRecordEntityList」；用「通知设置」而不是「Webhook 配置」。
- **使用主动语态**：按钮写「保存修改」「重新加载」「确认删除」，不要写含糊的「提交」。
- **动作名称保持一致**：按钮叫「保存修改」，成功提示就说「已保存修改」；不要按钮叫「发布」、结果叫「提交成功」。
- **错误说明发生了什么、怎么修**：写「网络连接失败，请检查网络后重试」，不要只写「系统错误」或「操作失败」。
- **空状态是行动邀请**：写「还没有餐补记录，导入本月数据后开始核对」并给下一步入口，不要只显示「暂无数据」。
- **加载状态说明正在做什么**：首次加载、刷新、提交、导出应有不同文案与视觉状态。
- **语气克制**：少用感叹号、营销词和拟人化道歉；界面应该帮助用户完成任务，而不是表演情绪。

```text
❌ 空状态：暂无数据。
✅ 空状态：还没有待核对的餐补记录。导入本月数据后，这里会显示需要处理的批次。

❌ 错误：操作失败。
✅ 错误：保存失败，可能是网络中断。请检查网络后重试，已填写的内容会保留。
```

## 11.10 页面必须有真实的状态，不是静态漂亮样板

一个可交付页面至少要有以下状态中的适用项：

- 首次加载 / 刷新中；
- 空状态；
- 请求失败与重试；
- 成功后的结果反馈；
- 提交中与重复提交防护；
- 无权限 / 未登录；
- 长内容滚动与底部安全区；
- 数据部分缺失或字段为空；
- 小屏与大字号下的可读性。

使用 `useQuery` / `useMutation` 时，加载、错误与空状态应以真实异步状态驱动，而不是用 `setTimeout` 伪造一个永远成功的页面。具体写法见 [分册 10](./10-http-spec.md)。

## 11.11 落到 uni-app X：设计必须服从原生渲染约束

设计计划不能只停留在视觉稿。以下约束直接决定设计是否可交付，完整正反例见 [分册 2](./2-styling.md)：

| 设计意图 | uni-app X 写法 |
| :--- | :--- |
| 页面布局 | 只用 flex；`flex-row` / `flex-col` / `flex-1` / `items-center` / `justify-between` |
| 元素间距 | `mt-*` / `mb-*` / `ml-*` / `mr-*`；禁止 `gap` / `space-x-*` / `space-y-*` |
| 字号 | 只用 `px`；禁止 `em` / `rem` / `%` / `vw` / `vh` |
| 文字颜色与字体 | 只挂 `<text>` / AppText；禁止挂 `<view>` |
| 原生按钮 | 用 `<view class="flex ...">` 包裹排版；按钮本身不挂 flex 对齐类 |
| 边框 | `border-[1px] border-solid border-[#e2e8f0]`，宽度、线型、颜色齐全 |
| 颜色 | 十六进制；语义色统一走 Token；换肤走 `useThemeStore()` |
| 安全区 | `p-safe` / `pt-safe` / `pb-safe` |
| 动态样式 | Vue 响应式 `:style`；动画关键帧固化在静态 class |
| 长列表 | 优先 `<z-paging-x>`；不要用 `100vh` 模拟整页滚动 |
| 字体与字号缩放 | AppText + `useFontStore()`；图标与第三方组件内部文字保持原样 |

### 11.11.1 先确认视觉方案可落地，再动手写页面

写代码前检查：

1. 设计是否需要浏览器专属能力（`backdrop-filter`、复杂 grid、hover、sticky、CSS `gap`）？如果需要，改设计，不要赌原生端能兼容。
2. 设计是否依赖大段自定义字体？如果是，确认字体文件、授权与加载失败兜底。
3. 设计的强调色是否只出现在一个地方？如果满屏都是强调色，先收敛。
4. 设计的 signature 是否会遮挡内容或破坏安全区？如果是，重做位置，不要靠 `z-index` 硬压。
5. 设计的空 / 错 / 加载状态是否完整？没有就先补状态，再谈视觉。

### 11.11.2 跨端验收

- 至少在 H5 与 Android App 各看一遍；涉及小程序时再补微信 / 支付宝真机。
- 检查小屏、大字号缩放、长文本、数字金额、空数据与错误状态。
- H5 表单与可操作控件保留清晰键盘焦点；App / 小程序至少提供明确的按压或选中反馈。
- 用截图对照设计计划，检查层级、间距、对比度与触控区域，而不是只看代码是否编译通过。
- 编译通过只代表「能运行」，不代表「设计可交付」。

## 11.12 设计自检清单

- [ ] 我能用一句话说清页面唯一任务与目标用户。
- [ ] 设计线索来自业务本身，而不是先选了组件库皮肤。
- [ ] 基础色不超过 6 个，全部为具名十六进制 Token。
- [ ] 正文、次要文字与按钮文字对比度足够，重要信息不靠极浅灰或纯色块大小硬撑。
- [ ] 强调色只服务于主操作 / 当前状态 / signature，没有到处发散。
- [ ] 字号层级不超过 5 级，没有无语义的字号碎片。
- [ ] 业务文案使用 AppText，字体与字号缩放可被全局设置影响。
- [ ] 没有把字体、字号、颜色挂到 `<view>` 上。
- [ ] 没有 `grid` / `inline-block` / `sticky` / `gap` / `space-*`。
- [ ] 编号、分割线、标签、eyebrow 都在编码真实信息。
- [ ] 页面只有一个主要记忆点，其余区域克制、统一。
- [ ] 动效只服务一个明确变化，不依赖动画传达关键信息。
- [ ] 空状态、错误、加载、提交中状态都有可执行下一步。
- [ ] 文案从用户视角命名，动作用主动语态，名称前后一致。
- [ ] 没有默认套用奶油衬线、近黑荧光、紫蓝玻璃、全卡片阴影等 AI 常见模板。
- [ ] 已在 H5 与 Android App（必要时加小程序）截图验收。

## 11.13 快速参考表

| 现象 / 问题 | 先做什么 | 不要做什么 |
| :--- | :--- | :--- |
| 页面像模板 | 回到 11.1 写业务主体、受众、唯一任务 | 继续加卡片、渐变和阴影 |
| 颜色很乱 | 收敛到 4–6 个具名 Token | 每个区块换一种强调色 |
| 字号层级不清 | 固定 3–5 级 type scale，统一走 AppText | 用 11–18px 的随机字号补差异 |
| 页面没有记忆点 | 只设计一个 signature | 给每个模块都加「特色」 |
| 空页面很尴尬 | 写行动型空状态并给下一步入口 | 只写「暂无数据」 |
| 错误提示很空 | 说明发生了什么 + 怎么恢复 | 只写「失败」或「系统异常」 |
| App 上样式不生效 | 读分册 2，检查 flex / 单位 / 文本宿主 / 边框 / 安全区 | 按 Web CSS 经验继续猜 |
| 页面数据是假的 | 接 `src/api/<module>/`，用真实 loading / error / empty 状态 | 用 setTimeout 永久显示成功样板 |
| 改版会影响旧链接 | 先确认是否保留原 URL 与信息架构 | 擅自移动页面或合并业务模块 |
